# 훈민바름 영어확장판 4본의 구성

훈민바름 영어확장판은 하나의 체계를 네 역할로 나눈다. 선언본은 뜻과 공공적 필요를 밝히고, 해례본은 정본의 구조와 발음 원리를 풀며, 전산본은 정본의 디지털 보존·처리 규격을 세우고, 구현본은 실제 프로그램과 시험으로 그 작동을 확인한다.

| 문서 | 담당 범위 | 이 책과의 관계 |
| --- | --- | --- |
| 제1본 선언본 | 뜻과 미래, 공공적 필요 | 목적과 연구 지위를 받는다. |
| 제2본 해례본 | 영어 RP·GA 음가와 블록 문법 | 무엇을 보존할지 정한다. |
| 제3본 전산본 | 구조·직렬화·표시·교환 규격 | 구현과 시험의 기준이다. |
| 제4본 구현본 | 웹 사용·실행·시험·공개 기록 | 실제 구현 범위와 차이를 밝힌다. |

## 이 문서의 지위

‘훈민바름’은 옛한글·확장 한글 자모를 활용한 「외국어 표기법」의 가능성을 연구·개발하는 동안 사용하는 내부 코드명이다. 현재 영어확장판은 가표본(working specimen) 연구이자 참조 실험(reference experiment)이며, 그대로 채택하도록 요구하는 공적 규범이 아니다.

이 개정은 2026-08-07 제4본의 12개 장과 부록 A·B를 계승한다. 설명과 예시는 2026-09-08 제1·2본 교정본, 46쪽 제3본 개정 초안 및 같은 날의 새 웹앱에 맞췄다. 구판의 규칙이나 시험 수치를 최신 구현의 사실로 옮기지 않는다.

## 읽는 길

처음 쓰는 독자는 §3과 §7부터, 수업에 활용하는 교사는 §6·7·8부터 읽을 수 있다. 개발자는 §4·5·9·10과 부록의 재현 조건을 함께 확인한다. 공개 저장소에는 문서와 코드가 함께 있으며, 실제 웹사이트의 서비스 상태는 저장소 파일 공개와 별도로 확인한다.

> 현재 구현은 제3본 기준의 Broad 시범 변환기다. 전체 규격의 적합성 인증, 전 사전 발음 검수 완료 또는 교육 효과 입증을 뜻하지 않는다.

# 머리말 · 구현은 규격을 대신하지 않는다

훈민바름 웹앱의 역할은 원어의 소리와 정본의 구조가 디지털 환경에서 얼마나 충실하게 보존되는지 드러내는 데 있다. 입력한 IPA가 어떤 음운 단위로 분석됐는지, 그 단위가 어떤 자모값과 위치형에 연결됐는지, 화면과 복사 결과가 무엇을 담고 무엇을 담지 못하는지를 확인할 수 있어야 한다.

화면이 그럴듯하다고 정본이 옳은 것은 아니다. 부호열이 규칙에 맞는다고 사전의 발음이 검수된 것도 아니다. 구현본은 이 차이를 구체적인 입력과 실행 결과로 설명한다. 미결을 미결로 남기는 결과도 연구 기록의 일부다.

# 1. 구현본의 목적과 권위 관계

## 1.1 규칙을 받는 방향

음가·자모값·손글씨 블록 문법은 제2본을 따른다. 구조 데이터와 Unicode 기준형은 제3본의 시범 규격을 따른다. 앱이 구현의 편의를 위해 고른 음절 추정법이나 화면 배치는 별도의 구현 선택으로 밝힌다. 이런 선택이 제2본의 새로운 최종 판정이 되는 것은 아니다.

예를 들어 현재 앱은 음절 경계가 없는 다중 모음핵 입력에 최대 초성 추정 휴리스틱을 사용한다. 이때 검토 필요 상태를 반환한다. 반면 IPA에 점으로 주어진 경계는 우선 보존한다. 같은 단어라도 분석 경계가 달라질 수 있는 이유를 이 기록에서 확인한다.

## 1.2 구현이 밝혀야 할 네 가지

첫째, 어떤 입력과 모듈을 사용했는가. 둘째, 어떤 규칙과 버전이 그 입력을 처리했는가. 셋째, 원문·강세·대응 관계가 어느 출력에 남아 있는가. 넷째, 아직 구현하지 못했거나 판정하지 않은 부분은 무엇인가.

구현과 문서가 다르면 입력, 등록부, 분석, 직렬화, 표시의 순서로 차이를 찾는다. 승인된 규칙 변경은 문서·코드·시험 벡터에 함께 반영한다. 기존 결과를 새 규칙의 정답으로 삼아 시험만 바꾸지 않는다.

# 2. 현재 참조구현의 구성

새 앱은 정적 HTML·CSS·JavaScript와 첨부 JSON 사전, 옛한글 웹글꼴로 구성된다. 변환을 위해 API 키나 외부 AI 호출을 사용하지 않는다. 브라우저가 필요한 사전 파일을 읽고, 변환 엔진이 그 IPA를 처리한다. 영어 철자에서 새 발음을 생성하는 모델은 포함하지 않는다.

## 2.1 사전 자료의 지위

첨부 GA 사전은 125,004개, RP 사전은 135,495개 항목을 담는다. 이는 파일의 항목 수이며 고유한 어휘 수나 검수된 발음 수를 뜻하지 않는다. 기존 자료는 GA를 CMU 계열, RP를 2023년 일부 기계 생성·검수 전 자료로 설명한다. 원 사전의 모든 IPA와 변이를 이번 개정에서 새로 검수하지 않았다.

문서 예시와 일반 사전 조회는 화면의 출처 표지로 구별한다. ‘문서 예시’는 책에 수록된 참조 입력이라는 뜻이며, 전체 사전의 품질 보증이 아니다. 수업용 새 어휘는 실제 source IPA와 선택 모듈을 교사가 먼저 확인한다.

## 2.2 이전 앱의 위치

legacy/index.html은 v2.0 계열의 비교용 화면이다. 원 코드의 Broad·Narrow·연음·조음 안내를 보존하되 현재 제3본의 적합 출력과 구분한다. 구버전의 동작 확인은 구버전 자체의 회귀시험이며 새 규격의 통과 증거가 아니다.

# 3. 사용자가 거치는 기본 흐름

## 3.1 영어로 찾기

‘영어로 찾기’를 선택하고 단어나 짧은 문장을 입력한다. ‘발음 기준’에서 RP 또는 GA를 선택한 뒤 ‘훈민바름으로 보기’를 누른다. 입력란에서는 Ctrl+Enter 또는 Command+Enter로도 변환할 수 있다.

처음에는 ‘책 속의 예시’에 있는 boost, play, friend, cats, about를 차례로 확인하는 편이 결과 구조를 익히기 쉽다. 영어 조회는 선택한 모듈의 문서 예시를 먼저 찾고, 없으면 첨부 사전을 읽는다. 일반 문장은 어휘별 결과의 배열이며 연결발화를 자동 재현한 결과가 아니다.

## 3.2 IPA 직접 입력

‘IPA 직접 입력’을 선택하고 Broad IPA를 넣는다. 전체를 / /로 감싸거나 기호 본문만 입력할 수 있다. 공백은 단어 사이, 점(.)은 음절 사이 경계로 사용한다. 예를 들어 /ə.ˈbaʊt/는 두 음절과 둘째 음절의 제1강세를 명시한다.

| 입력 | 확인할 사항 |
| --- | --- |
| /buːst/ | 한 모음핵, 한 음절블록 |
| /ə.ˈbaʊt/ | 두 블록, 둘째 블록의 제1강세 |
| /pɪk kæts/ | 두 단어, 두 개의 레코드 |
| /vɛɹi/ | 음절 경계 자동 추정과 검토 필요 표시 |
| /kætʃ/ | 종성 위치형 미배당, 직렬화 미결 |

## 3.3 결과를 읽는 순서

먼저 원문 IPA와 출처 표지를 확인한다. 그다음 〔 〕 한 쌍을 한 음절블록으로 읽는다. 자음군이나 긴 모음이 여러 요소로 보이더라도 같은 괄호 안이면 하나의 영어 음절이다. 끝으로 ‘IPA · 자모 대응 · 코드포인트’를 열어 입력 음소와 자리별 부호를 대조한다.

‘시범 변환’은 표시 완료의 상태다. ‘검토 필요 · 시범 변환’이면 자동 음절 추정 또는 미검수 사전 등의 조건을 함께 살핀다. ‘미결 항목 있음’이면 그 아래 사유를 먼저 읽는다.

# 3. 복사·저장·입력 오류의 처리

## 3.4 자모열 복사

‘자모열 복사’는 NFD 조합형 자모열을 복사한다. 화면의 괄호, 크기, 출처 표지는 포함하지 않는다. 단어 하나의 기준형 안에는 편집용 공백이 없다. 여러 단어를 함께 복사할 때만 단어별 자모열을 공백으로 연결한다.

전체 결과에 미결 단어가 있으면 전체 자모열 복사 버튼을 비활성화한다. 누락된 음소를 빼고 나머지만 완성 결과처럼 복사하는 일을 막기 위한 동작이다. 자동 클립보드 쓰기가 실패하면 수동으로 선택해 복사할 입력란을 표시하도록 구현돼 있다. 이 경로의 실제 브라우저별 동작은 별도 시험 대상이다.

## 3.5 전체 기록 저장

‘전체 기록 저장’은 hmbr-records.json을 내려받도록 구현돼 있다. 원입력, 선택 모듈, 원문 IPA, 정규화 이력, 강세, 음소와 자모의 대응, 직렬화 상태와 미결 사유가 기록된다. 수정·재검토·수업 자료 관리에는 평문만 보관하는 것보다 이 레코드가 적합하다.

저장 파일명은 고정이므로 내려받은 후 단어·모듈·검토일을 포함하는 이름으로 구별해 보관한다. 현재 화면에는 이 JSON을 다시 불러오는 가져오기 기능이 없다. ‘저장 가능’과 ‘앱에서 재열기 가능’을 혼동하지 않는다.

## 3.6 입력 오류와 미결의 차이

영어 조회에서 사전에 없는 단어가 하나라도 있으면 문장 전체의 변환 결과를 만들지 않고 해당 단어를 알린다. IPA를 알고 있다면 직접 입력으로 바꿀 수 있다. 이때도 모듈·음절 경계·출처를 별도로 확인한다.

IPA 직접 입력은 단어별 레코드를 만든다. /pɪk kætʃ/처럼 일부가 미결이면 가능한 단어와 미결 단어를 함께 보여 주며 전체 JSON에는 두 상태가 모두 남는다. 한 번에 100단어, 전체 입력 5,000자, 단어별 IPA 1,000자의 제한이 있다.

> 새 입력을 편집하면 이전 결과와 저장 가능 상태를 무효화한다. 입력문과 오래된 결과가 다른데도 같은 결과로 복사되는 일을 줄이기 위한 처리다.

# 4. 변환 파이프라인

## 4.1 원문에서 음절분석까지

영어 입력이면 사전 조회로 source IPA를 얻는다. IPA 직접 입력이면 사용자의 기호열을 원문으로 받는다. 이후 기호 별칭과 길이 부호를 처리하면서 바꾸기 전후와 규칙 식별자를 normalization_rules에 남긴다. GA /ɚ/는 원문을 보존하고 /əɹ/로 분석한 이력을 기록한다. /ɝ/의 미결 기저 모음을 같은 방식으로 임의 보충하지 않는다.

토큰화는 /tʃ/와 /dʒ/ 같은 등록 파찰음을 하나의 음운 단위로 인식한다. 음절분석은 입력 경계·강세 표지와 현재의 추정 규칙을 사용한다. 여러 음절의 자동 분석에는 검토 필요 상태를 남긴다.

## 4.2 음소와 자모 요소의 대응

canonicalModel은 phonemeTokens, mappingUnits, blocks를 가진다. 음소를 곧바로 한 글자와 동일시하지 않는다. /uː/ 하나는 두 JV-U 요소로, 종성의 /t/와 /s/ 두 토큰은 JV-TS 하나로 연결된다. 각 블록은 초성군·음절핵·종성군의 요소 참조를 순서대로 가진다.

| boost의 단위 | 소비한 음소 | 출력 자모 요소 |
| --- | --- | --- |
| m1 | /b/ | JV-B |
| m2 | /uː/ | JV-U, JV-U |
| m3 | /s/ | JV-S |
| m4 | /t/ | JV-T |

boost의 블록은 onset에 m1의 첫 요소, nucleus에 m2의 두 요소, coda에 m3·m4의 첫 요소를 둔다. 같은 입력 토큰을 중복 소비하거나 같은 출력 요소를 두 자리에 다시 두면 구조 검사에서 거부한다.

## 4.3 직렬화와 반환

모든 위치형이 배당되고 분석 문제가 없으면 L+ V+ T* 자모 연쇄를 만든다. 미배당이나 미지원 입력이 있으면 단어 전체 serialization.text를 null로 두고 원문과 구조, 사유를 반환한다. 출력의 status·필드명은 제3본 문서 예시와 일부 다르므로 §10의 대응표를 함께 읽는다.

# 5. 출력층과 화면 표시

구판의 ‘네 출력층’이라는 설명은 보존 목적을 이해하는 데 도움이 되지만, 실제 새 앱의 필드명과 일치하지는 않는다. 아래는 현재 코드에 존재하는 필드를 기준으로 한 구분이다.

| 실제 필드 | 담는 정보 | 용도 |
| --- | --- | --- |
| source, normalization_rules | 원철자·원문 IPA·출처·정규화 이력 | 원자료 확인 |
| canonicalModel | 음소·대응 단위·음절·강세 | 구조 보존 |
| serialization | 프로파일·상태·자모열·코드포인트 | 복사와 부호 검사 |
| display | 표시 프로파일과 블록별 요소 | 화면 배치 |
| analysis, issues, warnings | 분석 방식·미결·경고 | 검토와 오류 추적 |

## 5.1 한 블록과 여러 글리프

현재 표시 프로파일은 linear-elements-v1이다. 한 블록을 괄호로 묶고 자모 요소를 순서대로 배치한다. 압축된 한 네모꼴 자형을 모든 음절에 자동 합성하는 렌더러가 아니다. 보이는 글리프 수를 영어 음절 수로 세지 않는다.

pass의 종성 /s/는 같은 블록의 coda 요소다. 별도의 영어 음절블록을 만드는 것이 아니다. 직렬화에서는 U+11BA를 음소 순서에 놓고, 화면에서는 독립 요소로 식별할 수 있게 한다. 구판의 ‘/pæ/ 중심 블록과 별도 /s/ 블록’ 설명은 이 개정의 구조 설명으로 사용하지 않는다.

## 5.2 크기와 보존 정보

제1강세는 125%, 제2강세는 100%, 무강세는 75%로 표시한다. 강세 미지정은 기본 크기 100%이며 제1강세로 추정하지 않는다. 사용자가 글자 크기를 바꾸면 이 비율을 유지한다.

제2본의 장모음 뒤 요소 50% 시범 표시는 새 화면에 아직 별도로 구현되지 않았다. 현재 두 모음 요소는 해당 블록의 같은 크기를 따른다. 길이값은 IPA 토큰과 두 요소의 대응에서 확인할 수 있지만 별도 length 필드도 아직 없으므로 완전한 문서 스키마 구현으로 소개하지 않는다.

# 6. RP·GA와 Broad·Narrow 제어

## 6.1 모듈을 바꾸는 것은 출발 발음을 바꾸는 일

RP·GA는 서로 다른 참조모듈이다. 영어 조회에서 모듈을 바꾸면 그 모듈의 예시 또는 사전 IPA를 다시 읽는다. 화면 자모만 바꾸는 기능이 아니다. 직접 입력에서는 사용자가 넣은 IPA가 선택한 모듈과 맞는지 확인한다.

| 예시 | RP 문서 입력 | GA 문서 입력 |
| --- | --- | --- |
| go | /ɡəʊ/ | /ɡoʊ/ |
| car | /kɑː/ | /kɑɹ/ |
| pass | /pɑːs/ | /pæs/ |

이 표는 수록된 문서 예시의 차이다. 모든 영국·미국 화자가 이 한 가지 발음을 사용한다는 주장이 아니다. 사전의 발음 변이 전체를 선택하는 화면도 현재는 없다.

## 6.2 새 앱의 Broad 범위

새 앱은 Broad 변환을 제공한다. [ ]로 감싼 Narrow 입력, 미등록 발음기호나 지원하지 않는 발음 부호를 완성된 Broad 출력으로 바꾸지 않는다. /j, w/는 기저값 명시형을 제공하되 모음과의 최종 결합형은 미결 경고를 남긴다.

Narrow는 기저 음소를 지우는 모드가 아니다. 제2·3본에서는 Broad를 보존하고 표면 이음·환경·규칙을 별도 층에 추가하도록 요구한다. GA 탄설음, dark L, 성문파열과 음절자음 등을 같은 완성도와 지원 상태로 묶어 말하지 않는다.

## 6.3 이전 앱을 비교할 때

Narrow·연음·조음 안내를 살필 때는 ‘이전 앱 비교’로 이동한다. 출력 차이가 보이면 우선 그 화면이 legacy인지 확인한다. 특히 구판의 /l/ 중복, /ʊ/와 /uː/의 처리, /t+s/와 /tʃ/의 구별을 최신 결과와 섞지 않는다.

새 앱에서 water의 /t/가 자동으로 [ɾ]로 바뀐다고 설명하지 않는다. 현재의 공개는 Narrow 정합화 완료를 뜻하지 않으며, 관련 후속 작업은 §10에 남긴다.

# 7. 핵심 시험어로 읽는 구현

## 7.1 음절·모음·자음군

pick /pɪk/에서는 KIT의 U+119D를 확인한다. 이를 현대 ㅣ의 U+1175로 바꾸면 다른 값이 된다. bank /bæŋk/와 friend /frɛnd/에서는 같은 블록 안에 자음이 여러 개 있음을 확인한다. 자모가 길게 펼쳐진다는 이유로 소리에 없는 모음을 더하지 않는다.

play /pleɪ/의 초성군에는 /p/ 다음 /l/이 한 번 있다. /eɪ/는 같은 음절핵의 두 모음 요소이며, 둘째 요소 앞에 새 ㅇ을 넣지 않는다. blue /bluː/도 /l/ 한 번과 하나의 긴 음절핵을 같은 원리로 살핀다.

## 7.2 한 토큰과 두 요소, 두 토큰과 한 요소

boost /buːst/는 /b uː s t/ 네 음운 토큰으로 분석되며 다섯 자모 요소를 가진다. 길이 부호를 독립 자음처럼 읽지 않는다. cats /kæts/는 /k æ t s/ 네 토큰을 세 자모 요소로 적는다. 이 차이를 ‘IPA · 자모 대응 · 코드포인트’에서 확인한다.

| 비교 | 살펴볼 차이 |
| --- | --- |
| /ʊ/와 /uː/ | FOOT 하나와 U U 연쇄는 다른 값 |
| cats와 catch | /t+s/ 두 음소와 /tʃ/ 한 음소 |
| pass와 pat (GA) | 종성 /s/와 /t/의 대립 |
| /pɪk/와 /ˈpɪk/ | 자모열은 같아도 강세 기록은 다름 |

## 7.3 미결을 읽는 예

‘catch 미결 예’ 버튼은 IPA 직접 입력으로 전환하여 /kætʃ/를 넣는다. 이때 원문과 /tʃ/ 토큰, 종성 자모값은 구조에 남지만 종성 위치형 부호가 미배당이므로 평문을 제공하지 않는다. cats의 성공 결과를 가져와 catch의 대체 표기로 삼지 않는다.

GA /nɝs/와 음절자음 입력도 별도의 미결 이유가 있다. 같은 ‘미결’ 표시라도 부호의 부재, 분석의 미결, 지원 범위 밖을 issues에서 구별해 읽는다.

# 7. 교사를 위한 사용해례

아래는 이번 구현본에서 제안하는 수업 절차다. 교육 효과를 검증한 실험 결과나 필수 교수 순서로 제시하는 것은 아니다. 학습자가 IPA와 훈민바름을 대조하고 한 음절의 범위를 읽게 하는 짧은 활동으로 사용할 수 있다.

## 7.4 활동 하나 · 자음군을 음절로 늘리지 않기

pick, bank, friend, boost를 차례로 제시한다. 먼저 교사가 실제 발음을 들려주거나 출처가 확인된 발음 자료를 준비한다. 이 앱에는 영어 낭독 기능이 없으므로 표기만 보고 발음 모델을 새로 정하지 않는다.

학습자에게 각 단어의 괄호가 몇 쌍인지, 음절핵이 어디인지, 앞뒤 자음이 어느 순서로 놓이는지 물어본다. bank의 끝에서 /ŋ/ 뒤 /k/가 이어져도 새로운 모음핵이 생기지 않는다는 점을 확인한다. 학습자의 발음은 별도로 듣고 피드백한다.

## 7.5 활동 둘 · 같은 철자, 다른 참조 발음

go, car, pass를 RP와 GA로 각각 조회한다. 먼저 source IPA의 차이를 찾고 그다음 자모열의 차이를 확인한다. 어느 쪽이 더 한국어처럼 읽히는지보다 어떤 원어 소리 정보를 보존하는지 설명하게 한다.

결과를 기록할 때는 단어만 적지 않고 모듈과 원문 IPA를 함께 적는다. 사전 출처가 다른 자료와 비교할 때는 발음 차이가 구현 오류인지, 출처의 다른 변이인지 먼저 판단한다.

## 7.6 활동 셋 · 저장할 정보 선택하기

/ə.ˈbaʊt/를 변환한 뒤 자모열 복사와 전체 기록 저장의 차이를 설명한다. 강세가 어느 출력에 남는지, source IPA와 출처를 나중에 확인하려면 무엇을 보관해야 하는지 학습자가 답하게 한다.

마지막으로 cats와 catch를 비교한다. ‘미결’이 단어를 발음할 수 없다는 뜻이 아니라 현재 프로파일이 완성 평문을 내보낼 조건을 갖추지 못했다는 뜻임을 확인한다. 결과를 비판적으로 읽는 능력도 활동의 목표다.

> 교사의 준비 기록: 목표 단어·모듈·확인한 IPA·음성자료 출처·앱 커밋·기대 결과를 함께 남긴다. 이 절은 새로 제안한 활용안이며 기존 문서의 확정 규칙과 구분한다.

# 8. 글꼴·셰이핑과 대체 표시

## 8.1 부호가 있는 것과 잘 보이는 것은 다르다

등록된 코드포인트가 글꼴에 들어 있다는 사실만으로 임의의 복합 음절이 압축된 한 자형으로 보인다고 판단할 수 없다. 글꼴의 지원, 브라우저의 셰이핑, 화면에서 요소를 나누는 방식, 복사되는 문자열을 각각 확인한다.

새 앱은 두 옛한글 WOFF를 같은 사이트의 fonts/에서 읽는다. 현재 기본 화면은 자모 요소를 별도 요소로 배치하는 선형 시범형이다. 따라서 제3본의 특정 OTF·HarfBuzz 계측 수치를 이 웹화면의 폭이나 글리프 수로 옮겨 쓰지 않는다.

## 8.2 검증할 화면 조건

| 조건 | 확인할 내용 |
| --- | --- |
| 단순 음절 | KIT·FOOT 등 모음값 식별 |
| 복합 음절 | 한 괄호 안의 요소 순서와 누락 여부 |
| 종성 /s/ | /t/와 구별되고 읽는 순서가 보이는지 |
| 크기 변경 | 강세 비율, 잘림, 행간 충돌 |
| 좁은 화면 | 입력·결과·대응표의 가로 넘침 |
| 글꼴 로드 실패 | 대체 글꼴과 누락 문자의 인지 가능성 |

## 8.3 현재의 대체 표시와 남은 기능

현재 앱은 직렬화 미결을 원문 IPA와 사유로 설명하고, 코드포인트와 대응표를 제공한다. 다만 브라우저에서 글리프 누락을 자동 감지하여 missing_glyph나 render_status를 기록하는 기능은 없다. 화면에 네모가 보인다면 부호 미배당인지, 글꼴 문제인지, 선형 표시의 한계인지 나누어 살펴야 한다.

## 8.4 접근성의 검증 범위

입력 라벨, 키보드로 이동할 수 있는 기본 제어, 변환 상태 알림, 결과의 설명 텍스트가 코드에 있다. 이 사실만으로 화면낭독기의 정확한 발음이나 접근성 적합성을 선언하지 않는다. 강세가 크기와 마우스 설명에 의존하는 부분, 모바일 조작과 낭독기의 읽는 순서는 실제 환경에서 추가 확인해야 한다.

## 11.5 증상별로 먼저 볼 것

‘사전에 없는 단어’이면 철자와 문장부호를 확인한다. 사전이 없다는 이유로 발음을 추측하지 않으며, 확인한 IPA가 있을 때 직접 입력한다. ‘사전 파일을 불러오지 못했습니다’이면 HTTP 실행과 파일 경로를 확인한 뒤 다시 시도한다. 실패한 사전 요청은 캐시에서 제거해 재요청할 수 있도록 구현돼 있다.

‘직렬화 미결’이면 issues에서 미배당 위치형과 분석 미결을 구별한다. /θ ð ʒ tʃ dʒ/의 종성이 해당되면 현 등록부의 제한일 수 있다. 익숙한 현대 한글로 대체해 성공 처리하지 않는다.

자모가 깨져 보이면 원문 IPA와 코드포인트부터 확인한다. 부호열이 맞다면 글꼴 다운로드와 표시 경로를 살핀다. 복사한 내용에서 강세가 보이지 않는 것은 평문 복사의 범위일 수 있으며, 전체 기록의 블록 stress를 확인한다.

# 12. 향후 다언어 구현 원칙

## 12.1 영어를 공통 규칙으로 강제하지 않기

영어 참조구현은 다른 언어의 정답을 미리 정하지 않는다. 새 언어는 원문 문자, 언어·지역 식별, source IPA, 자체 음운 단위, 음절구조, 강세·성조와 실제 화자 검토를 갖춘 독립 모듈로 추가한다.

공통으로 재사용할 부분은 원문 보존, 자모값 등록 절차, 음운 토큰과 자모 요소의 분리, 구조와 표시의 분리, 버전·시험 기록이다. 영어의 RP·GA 모음값이나 음절 추정 규칙을 다른 언어에 그대로 적용하지 않는다.

## 12.2 새 모듈을 위한 최소 자료

출처가 확인된 입력 집합과 발음 변이, 자모값 대응표, 위치형의 지원 상태, 음절분석 근거, 양성·부정·미결 시험을 마련한다. 기존 자모값을 재사용할 때는 음가와 역규칙이 맞는지 확인한다. 모양이나 Unicode 이름의 유사성만으로 동치를 선언하지 않는다.

신규 모듈이 기존 자료의 해석을 바꾸면 새 모듈·등록부 버전으로 구별한다. 과거 레코드를 새 규칙으로 다시 계산할 때는 source와 이전 버전을 보존하며, 원자료가 없는 출력만으로 원래 발음을 확정하지 않는다.

## 12.3 바르미의 다른 구성과 연결하기

MetaVoc 선택 화면, Seesaurus와의 자료 연결, 종합 학습 과정은 현재 새 웹앱에 포함돼 있지 않다. 향후 어휘 자료를 연결할 때도 표제어만 넘기지 않고 IPA·모듈·출처·검수 상태를 함께 전달해야 한다. 교육용 화면을 확장하는 일과 훈민바름의 음가 규칙을 바꾸는 일은 별도로 관리한다.

## 맺음말 · 구현은 보존을 보여 준다

좋은 참조구현은 가능한 결과를 보여 주고, 그 결과를 다시 검사할 근거를 남긴다. 원어의 소리를 정본에 담는 원리, 데이터를 잃지 않는 형식, 사람이 읽을 수 있는 화면이 서로를 검증할 때 연구는 다음 단계로 나아간다. 이 구현본은 그중 오늘 실제로 작동한 부분과 다음에 검증할 부분을 함께 기록한다.
